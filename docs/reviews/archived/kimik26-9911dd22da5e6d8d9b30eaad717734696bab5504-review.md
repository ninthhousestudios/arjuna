## File-by-File Review

### `arrow/swe/lib/src/julian_day.dart` (new)

**Correctness — minor bug in `fromJulianDay`:**

```dart
final millisecond = ((totalSeconds - second) * 1000.0).round();
```

Floating-point error can push this to `1000`, which is out of range for `DateTime.utc`. Dart's `DateTime` constructor normalizes some out-of-range values, but milliseconds are clamped to `0–999`; `1000` may throw `ArgumentError` depending on the VM version. Safer:

```dart
final millisecond = ((totalSeconds - second) * 1000.0).round().clamp(0, 999);
```

**Coverage gap:** No tests for pre-1582 (Julian calendar) dates. The doc comment honestly notes "accurate to the millisecond for dates in the Gregorian calendar (post 15 Oct 1582)," which aligns with the Meeus algorithm used. That's acceptable for Phase A, but add a guard or explicit test if you ever expose this to user input.

### `quiver/server/lib/src/isolate_pool.dart` (new)

This is the most complex new file. Several issues:

**1. Worker initialization failure = infinite hang**

```dart
final isolate = await Isolate.spawn(
  _workerEntryPoint,
  _WorkerInit(...).toMessage(),
);
final workerSendPort = await initPort.first as SendPort;
```

If `_workerEntryPoint` crashes during `SwissEph.find()` or `SweFacade(...)` construction, it never sends on `init.sendPort`, so `await initPort.first` hangs **forever**.

**Fix:** Add a timeout to `initPort.first` (e.g., `Future.any([initPort.first, Future.delayed(Duration(seconds: 10)).then((_) => throw StateError('Worker init timeout'))])`), or move the `SweFacade` construction into the `receivePort.listen` block with an explicit error-send on the init port.

**2. `dispose()` can hang on orphaned completers**

```dart
await Future.wait(
  _pending.values.map((c) => c.future.catchError((_) {})),
);
```

If a worker is killed or crashes **after** `_disposed = true` but **before** it responds, the completer never completes, and `dispose()` hangs indefinitely. This is a real risk in containerized deployments where SIGTERM triggers shutdown.

**Fix:** Add a timeout wrapper around each pending future, or cap the shutdown grace period:

```dart
await Future.wait(
  _pending.values.map(
    (c) => c.future
      .timeout(Duration(seconds: 5), onTimeout: () => throw StateError('Shutdown timeout'))
      .catchError((_) {}),
  ),
);
```

**3. Race between response and dispose**

If a response arrives while `dispose()` is executing but before `rp.close()`, the receivePort listener will find the completer in `_pending` and complete it. That's fine. But if the response arrives **after** `rp.close()`, the message is dropped and the completer never completes (again, hang). A timeout fixes this generically.

**4. Request ID overflow**

`_nextId` is an `int` with no wraparound logic. In a long-running server, this will eventually overflow. Dart `int` is arbitrary-precision on native, so it won't wrap negatively, but it will grow without bound. Not a practical issue for most workloads, but worth a comment.

**5. No retry on worker death**

If an isolate dies after initialization, the pool doesn't detect it. `Isolate.addOnExitListener` could be used to recycle dead workers. For Phase A, document as a known limitation.

### `drishti/lib/src/server.dart` (new)

- **SIGTERM not handled:** Only SIGINT is trapped. In Docker/Kubernetes, SIGTERM is the standard graceful-shutdown signal. Add:

- **Keep-alive anti-pattern:** As noted in Architecture, the `Future.delayed(Duration(days: 365))` should be replaced with a `Completer` or transport close listener.
