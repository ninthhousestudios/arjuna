## 1. Executive Summary

This commit delivers the entire Phase A infrastructure layer: four distinct subsystems (Julian Day conversion, Vayu embedded facade, Drishti MCP server, IsolatePool) plus melos/pubspec config migration and proto codegen scripting. It transforms Arrow from a multi-package library requiring manual wiring into something consumable via three clean entry points: in-process (`Vayu`), MCP protocol (`Drishti`), and gRPC with isolate parallelism (`IsolatePool` via `ArrowGateway`).

The code is **idiomatic Dart 3, well-structured, and substantially tested**. The architecture cleanly respects the existing layer boundaries (SWE → Core → Calc). However, this is a *large* commit combining five orthogonal concerns, and there are several issues ranging from a significant correctness risk (IsolatePool JSON serialization through freezed-generated codecs) to design concerns (Drishti server lifecycle, melos config duplication, round-robin dispatch semantics).

**Overall Grade: B+**

Strengths: Vayu is a clean, minimal facade; Julian Day is well-tested with round-trip verification; IsolatePool has the right shape for Dart FFI+isolate concurrency; test coverage is solid. Issues below are ordered by severity.

## 3. Correctness Issues

### 3.1 [High] IsolatePool serialization relies on freezed-generated `toJson`/`fromJson` which may silently drop data

**File:** `quiver/server/lib/src/isolate_pool.dart:70-76, 108-114`

The IsolatePool serializes `ArrowOptions` and `Location` as JSON strings via `jsonEncode(options.toJson())` and deserializes with `ArrowOptions.fromJson(jsonDecode(...))`. Similarly for `EphSnapshot` in the response path.

Freezed-generated `toJson`/`fromJson` round-trips correctly *for the fields freezed knows about*. But the `EphSnapshot` type contains `Map<Body, BodyPosition>` and `Map<Body, PhenoData>` — these use custom `BodyMapConverter` / `BodyPhenoMapConverter` serializers that map `Body` enum keys to `.name` strings. The freezed `.g.dart` code invokes these converters.

**Risk:** If any `BodyPosition`, `PhenoData`, `AscMcPoints`, or `SunTimes` sub-object adds a new field in a future commit but the `.g.dart` is not regenerated, `fromJson` will silently ignore the new field on the deserialization side. The worker isolate would produce a correct `EphSnapshot` locally, but after JSON round-trip the main isolate would see a degraded snapshot missing the new field. There is no schema version check or structural equality assertion.

**Mitigation:** Add a post-deserialization sanity check comparing `snapshot.toJson()` round-tripped back through `fromJson`. Or better: since Dart isolates support `SendPort` messaging with arbitrary object graphs (pending `package:isolates` or `Isolate.resolvePackageUris`), consider using `TransferableTypedData` + binary serialization (protobuf, msgpack) for the cross-isolate boundary. The current JSON-string-in-a-list approach works today but is fragile under schema evolution.

### 3.2 [High] Drishti server `await Future.delayed(Duration(days: 365))` is a dangerous keep-alive pattern

**File:** `drishti/lib/src/server.dart:42-43`

```dart
await Future<void>.delayed(const Duration(days: 365));
```

This is used as a "keep alive" mechanism so `startServer` doesn't return. But:

1. If someone calls `startServer()` and later needs to stop it programmatically, they'd need to wait up to a year.
2. The SIGINT handler calls `exit(0)` — this bypasses Dart's event loop cleanup. `dispose()` on Vayu calls `SwissEph.close()` which releases native resources, but `exit(0)` may not give the event loop enough time to process the closing if the native shutdown takes any async work.
3. If the MCP transport closes (client disconnects), the function *still* waits 365 days.

**Recommendation:** Replace with a `Completer<void>` that is completed by either SIGINT or transport disconnect. The MCP `StdioServerTransport` likely exposes a `onClose` callback — wire that into the same shutdown path. Example:

```dart
final done = Completer<void>();
ProcessSignal.sigint.watch().listen((_) async {
  _log.info('SIGINT received, shutting down');
  vayu.dispose();
  await server.close();
  done.complete();
});
await done.future;
```

### 3.3 [Medium] `_handleCalculateChart` silently falls back to `ernst` on unknown preset

**File:** `drishti/lib/src/tools/calculate_chart.dart:87-90`

```dart
final options = switch (presetStr) {
  'ernst' => ArrowPresets.ernst,
  'lahiri' => ArrowPresets.lahiriVedic,
  'western' => ArrowPresets.westernTropical,
  _ => ArrowPresets.ernst,
};
```

The `_` wildcard silently falls back to `ernst`. The user could pass `preset: 'lahri'` (typo) and get `ernst` results with no warning. This violates the principle of least surprise — an astrological calculation returning wrong-tradition results silently is particularly dangerous.

**Recommendation:** Return an error result for unknown presets:

```dart
_ => null,
```

Then check if `options` is null and return `_errorResult('Unknown preset: $presetStr. Valid: ernst, lahiri, western')`.

### 3.4 [Medium] IsolatePool round-robin dispatch has no backpressure or timeout

**File:** `quiver/server/lib/src/isolate_pool.dart:124-140`

The `calculate` method dispatches to the next worker in round-robin order with no consideration of whether that worker is busy. A slow calculation on worker 0 will queue up messages while worker 1 sits idle. Under load, the round-robin creates unbounded per-isolate queues since `ReceivePort.listen` has no backpressure.

**Recommendation for now:** Document this limitation clearly — round-robin is fine for low-to-medium concurrency where calculations have roughly uniform latency. For production, consider a work-stealing or least-loaded dispatch strategy. Also add a timeout parameter to `calculate()` so callers aren't blocked forever if an isolate hangs.

### 3.5 [Low] `fromJulianDay` rounding can produce millisecond=1000

**File:** `arrow/swe/lib/src/julian_day.dart:43-44`

```dart
final millisecond = ((totalSeconds - second) * 1000.0).round();
```

If `totalSeconds - second` is e.g. `0.9999995`, `round()` produces 1000, which is invalid for `DateTime`. The probability is low (requires sub-microsecond precision hitting exactly this boundary) but the Meeus reverse algorithm's floating-point accumulation makes it possible.

**Recommendation:** Clamp: `millisecond.clamp(0, 999)`, or use `.truncate()` instead of `.round()` and accept small precision loss.

### 3.6 [Low] Drishti doesn't validate the `--ephe-path` argument exists as a directory

**File:** `drishti/bin/drishti.dart:6-10`

If `--ephe-path /nonexistent` is passed, Vayu creates `SweFacade` which calls `_swe.setEphePath(...)` — Swiss Ephemeris silently falls back to Moshier精度. The user gets wrong results with no error, which is particularly insidious for an MCP tool that AI agents trust.

## 4. Design & Architecture

### 4.1 Good: Vayu is a clean facade with correct lifecycle management

The `Vayu` class is exemplary in its simplicity: three methods, a private constructor wrapping `SwissEph` + `SweFacade`, and a `dispose()` with `_disposed` guard. The separation of `calculateChart` vs `calculateSnapshot` vs `recalculate` maps exactly to the SweConfig/CalcConfig architecture split described in CLAUDE.md. The `_checkNotDisposed()` pattern matches the existing `SweFacade` approach.

### 4.2 Good: `ArrowGateway` async refactor is well-designed

The `SnapshotCalculator` typedef cleanly abstracts over sync `SweFacade` and async `IsolatePool.calculate`. The factory constructor `ArrowGateway(SweFacade)` preserves backward compatibility. The change from sync `calculateChart` to `async` is a minimal but necessary API evolution.

### 4.3 Good: Julian Day follows Meeus exactly with proper attribution

The code clearly references "Meeus formula (Astronomical Algorithms, Jean Meeus)" and handles the Gregorian/Julian calendar transition (cutover at 2299161). The tests verify J2000.0, Unix epoch, and a known historical date — all correct reference values.

### 4.4 [Medium] `chart_formatter.dart` duplicates sign/nakshatra name lists that exist in arrow_core

**File:** `drishti/lib/src/formatting/chart_formatter.dart:7-56`

The `_signNames` and `_nakshatraNames` constants duplicate data that likely lives in `arrow_core` as part of the domain model. If `arrow_core` gains a sign-name enum or lookup, this will silently diverge.

**Recommendation:** Import the canonical sign/nakshatra naming from `arrow_core` if available, or at minimum add a comment acknowledging the duplication and linking to the authoritative source.

### 4.5 [Medium] Drishti `chart_formatter` is coupled to `Planet`/`Karaka`/`Cusp` via `is` runtime type check

**File:** `drishti/lib/src/formatting/chart_formatter.dart:76-78`

```dart
if (planet is Karaka) {
  result['dignity'] = planet.dignity.name;
  result['is_combust'] = planet.isCombust;
}
```

The `is Karaka` check is a code smell — it forces the formatter to know the type hierarchy. If a new Planet subtype with dignity information appears, the formatter won't pick it up. The test for this (`karakas have dignity field`) is correct but fragile.

**Recommendation:** Add a `dignity` getter to the `Planet` base class that returns `null` for non-Karaka types (or use an interface like `HasDignity`). The formatter then does `if (planet.dignity != null)` — no type check needed.

### 4.6 [Medium] IsolatePool `_pending` map grows unboundedly if responses are lost

**File:** `quiver/server/lib/src/isolate_pool.dart:92-115`

If a worker isolate crashes or the `ReceivePort` is closed unexpectedly, pending completers are never resolved. The `dispose()` method does handle this via `catchError`, but during normal operation there's no timeout or cleanup for orphaned entries.

**Recommendation:** Add a periodic sweep of `_pending` entries older than N seconds, completing them with a timeout error. Or simpler: give `calculate()` a `Duration timeout` parameter and use `completer.future.timeout(...)`.

### 4.7 [Low] Drishti `_inputSchema` doesn't specify `additionalProperties: false`

**File:** `drishti/lib/src/tools/calculate_chart.dart:18-38`

The MCP JSON schema object doesn't set `additionalProperties: false`, so a client could pass arbitrary extra parameters that are silently ignored. This isn't a functional bug but MCP best practice recommends strict schemas.

### 4.8 [Low] Julian Day `_meeus` double vs int mixing

**File:** `arrow/swe/lib/src/julian_day.dart:55-63`

```dart
final jd = (365.25 * (y + 4716)).floor() +
    (30.6001 * (m + 1)).floor() +
    day +
    hour / 24.0 +
    b -
    1524.5;
```

`(365.25 * (y + 4716)).floor()` — the product is a `double` (because `365.25` is double), then `.floor()` returns `int`. The `+` with `day` (int) and `hour / 24.0` (double) produces double. This works correctly in Dart but is worth noting: the Meeus formula should have integer arithmetic for the `(365.25 * ...)` and `(30.6001 * ...)` terms, and Dart's `.floor()` achieves this. The formula is correct.

## 5. Configuration & Build

### 5.1 [High] melos configuration duplicated between `melos.yaml` and `pubspec.yaml`

Both files now contain identical `melos:` configuration blocks (scripts, bootstrap settings). The `pubspec.yaml` version adds `--plugin=protoc-gen-dart=$HOME/.pub-cache/bin/protoc-gen-dart` while the `melos.yaml` version omits it. This means:

1. `melos run protogen` from `melos.yaml` may fail because it doesn't specify the plugin path.
2. `melos run protogen` from `pubspec.yaml` has the plugin path but is hardcoded to `$HOME/.pub-cache/bin/`.
3. Running `melos run analyze` or `melos run test` will execute whichever definition melos picks up first — the duplication is confusing.

The commit message says "migrated melos config to pubspec.yaml for Melos 7 compatibility", but the old `melos.yaml` is left intact and even augmented with a new `protogen` script. This creates a split-brain situation.

**Recommendation:** Delete the melos configuration from `melos.yaml` entirely (or delete the file), keeping only the `pubspec.yaml` version. If `melos.yaml` is still needed for Melos < 7 compat, add a comment explaining the split.

### 5.2 [Low] `protogen` script in `pubspec.yaml` uses hardcoded `$HOME` path

**File:** `pubspec.yaml:43`

```yaml
--plugin=protoc-gen-dart=$HOME/.pub-cache/bin/protoc-gen-dart
```

This won't work on Windows and assumes the protoc plugin is installed via `pub global activate protoc_plugin`. A more robust approach would use `dart pub global run protoc_plugin:protoc-gen-dart` or at least document the prerequisite.

## 6. Testing

### 6.1 Good: Julian Day test coverage is thorough

Three known-epoch tests (J2000.0, 1985-07-04, Unix epoch) plus round-trip in both directions with precision assertions. The sub-second precision test (`2460000.123456`) is a nice touch.

### 6.2 Good: Vayu tests cover all three methods + dispose guard

The `recalculate` test verifying `same(snapshot)` identity is important — it confirms no SWE recomputation occurs. The `dispose` test checks all three entry points throw `StateError`.

### 6.3 Good: IsolatePool concurrent request test

10 concurrent requests with distinct JDs, verifying each returns the correct JD. The comparison against direct `SweFacade` calculation (longitude, latitude, cusps, ascendant, MC) is crucial for validating serialization correctness.

### 6.4 [Medium] Drishti formatter tests rely on live SWE calculation

**File:** `drishti/test/tools_test.dart`

Every test calls `vayu.calculateChart(...)` which hits the real Swiss Ephemeris native library. This makes tests:

1. Slow (~1s per chart calculation across 15+ tests)
2. Dependent on the ephe data files being present
3. Non-deterministic if Swiss Ephemeris versions differ

**Recommendation:** Create a `Chart` fixture from a known snapshot (either via `Chart(EphSnapshot(...), config)` or by snapshotting once and storing as JSON). The formatter tests only need the domain model shape, not the SWE computation. A single integration test that exercises the full pipeline is sufficient.

### 6.5 [Medium] IsolatePool `dispose drains in-flight requests` test has a race condition

**File:** `quiver/server/test/isolate_pool_test.dart:93-115`

```dart
final futures = List.generate(5, (i) {
  return pool.calculate(testJd + i * 0.1, testLocation, testOptions);
});
await pool.dispose();
```

After `dispose()`, the code iterates through `futures` with `await f`. But `dispose()` already called `Future.wait(_pending.values.map(...))` internally and then killed isolates. The `await f` calls here will either resolve immediately (if the internal `Future.wait` already consumed them) or throw. The assertion `results.where((r) => r).length, greaterThan(0)` is weak — it passes even if only 1 of 5 completes. This doesn't actually test that *in-flight* requests complete; it tests that *some* may complete.

**Recommendation:** Use `Future.wait(futures)` before `dispose()` to confirm all complete, then separately test that post-dispose calls throw.

### 6.6 [Low] No test for Drishti `_handleCalculateChart` error paths

The tool handler has error paths for: missing date, invalid date format, invalid latitude, invalid longitude. None of these are unit-tested — only the formatter is tested. A mock-based test of `_handleCalculateChart` directly would catch regressions in parameter validation.

## 7. Style & Naming

### 7.1 Good: Naming follows convention

`Vayu`, `Drishti`, `IsolatePool` all follow the archery metaphor (Vayu = wind god, Drishti = sight/gaze). The MCP tool name `calculate_chart` uses snake_case per MCP convention.

### 7.2 [Low] `_CalcRequest` and `_CalcResponse` could use `SendPort`-safe structured messaging

The current approach converts to `List<Object>` / `List<Object?>` for `SendPort`. This works but is fragile — the field ordering must match exactly between `toMessage()` and `fromMessage()`, and there's no compile-time safety. A `Map<String, Object>` would be slightly more resilient, at marginal performance cost.

### 7.3 [Low] Drishti `startServer` mixes library and CLI concerns

**File:** `drishti/lib/src/server.dart`

`startServer` sets `Logger.root.level` and installs a `stderr` listener — this is CLI-level configuration that belongs in `bin/drishti.dart`, not the library. A library consumer might want different logging behavior.

## 9. Verdict

Phase A delivers real, working infrastructure. The Vayu facade is the right abstraction for in-process consumers; the IsolatePool is a solid first pass at concurrent SWE computation; Drishti makes Arrow accessible to AI tooling. The Julian Day module is clean and well-tested.

The main concerns are: (1) the IsolatePool JSON serialization layer is a correctness liability under schema evolution, (2) the Drishti server lifecycle pattern needs rework, and (3) the melos configuration duplication will cause confusion. These are all fixable without architectural changes and should be addressed before Phase B builds on top of this infrastructure.
