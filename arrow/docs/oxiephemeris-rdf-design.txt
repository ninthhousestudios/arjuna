## oxiephemeris-rdf — what it does

It's a **serialization/output layer** that converts computed astrological chart data (natal charts, transits, synastry comparisons, composites) into **RDF graphs**. It depends on `oxrdf` and `oxttl` — the low-level data model and Turtle serializer from the oxigraph ecosystem — but **not** on `oxigraph` (the store/query engine) itself.

Concretely it:
1. **Defines an OWL ontology** for astrology — classes like `NatalChart`, `Transit`, properties like `hasLongitude`, `inSign`, `hasAspect`, with multilingual labels (en/ja) via SKOS.
2. **Mints IRIs** for chart instances (content-addressed via SHA-256 of the epoch + observer).
3. **Emits triples** for every computed fact — body placements, house cusps, aspects, dignities, etc.
4. **Attaches PROV-O provenance** (which software version, which ephemeris file produced the data).
5. **Serializes** the resulting graph to deterministic Turtle or N-Triples.

The output is Linked Open Data: self-describing, portable, mergeable, queryable by anything that speaks SPARQL.

---

## How this relates to vidya + oxigraph

**vidya** wraps `oxigraph::store::Store` in its `KnowledgeStore` — a persistent RDF triple store you can load graphs into and query with SPARQL. It resolves domain vocabulary, manages named graphs per domain, and does schema-aware operations (synonyms, skolemization, etc.).

The connection is straightforward and complementary:

| | oxiephemeris-rdf | vidya |
|---|---|---|
| **Role** | *Producer* — generates RDF triples | *Consumer* — stores/queries/reasons over RDF |
| **Oxigraph dep** | `oxrdf` + `oxttl` (data model + serializer only) | `oxigraph` (full store + SPARQL engine) |
| **Output** | Turtle/N-Triples files | SPARQL query results, resolved entities |

**They sit at opposite ends of the same pipeline**: oxiephemeris-rdf produces well-typed Linked Data that something like vidya's KnowledgeStore could ingest directly — load the Turtle, query across charts, run SPARQL to find all transits with applying squares, merge charts from different sources, etc.

The "oxi" prefix is shared heritage — `oxrdf`, `oxttl`, `oxigraph`, `oxsdatatypes` are all from the [oxigraph project](https://github.com/oxigraph/oxigraph) by Thomas Tanon. oxiephemeris-rdf uses the lightweight serialization pieces; vidya uses the full engine. If you ever wanted to load astrological chart data into vidya's knowledge store, oxiephemeris-rdf's Turtle output would be the ingest format — no adapter needed, it's already valid RDF with a proper ontology.

Yes — if arjuna's calc engine emits RDF (using an ontology like oxiephemeris-rdf defines, or your own), you get a lot more than just "easier search." Let me lay out what RDF representation actually buys you over, say, storing charts as JSON/structs in a regular DB:

**What becomes trivial with charts-as-RDF in a store like vidya:**

1. **SPARQL queries across all charts** — "find every chart where Mars is in the 7th house applying a square to Venus within 3°" becomes a declarative query, not imperative code iterating over records. The graph structure means you don't need to pre-decide which questions are askable.

2. **Schema-aware merging** — charts from different sources (different calc engines, different house systems, different ephemerides) can coexist in the same store with provenance tracking. You know *which* engine produced *which* triples and can filter/compare accordingly.

3. **Inference/reasoning** — with an OWL ontology declaring class hierarchies (e.g., "a NatalChart is a Chart", "domicile is a DignityTier"), you get entailment for free. Query for "all dignity placements" and get domicile, exaltation, triplicity without enumerating them.

4. **Linked Data interop** — connect charts to external datasets. Link a birth chart's observer location to a Wikidata entity. Link planetary positions to JPL ephemeris identifiers. Once it's RDF, joining across datasets is just adding triples.

5. **Pattern libraries as data** — define aspect patterns, chart signatures, or traditional configurations (T-squares, grand trines, stelliums) as SPARQL graph patterns or SHACL shapes. Then *matching* is query execution, not custom code per pattern.

6. **Temporal/comparative queries** — "show me every transit where Saturn crossed my natal Sun across 40 years of computed transits" is one query if all those transits are triples in the store.

7. **Research corpus** — accumulate thousands of charts (from Astro-Databank, from clients, from historical records) and do statistical queries: "what percentage of charts with Sun in Aries also have Mars in a fire sign?" Exploratory analysis without writing bespoke aggregation code each time.

**The real unlock** isn't any single query — it's that you stop pre-deciding what questions matter. JSON/struct storage optimizes for the access patterns you anticipated. RDF lets you ask questions you haven't thought of yet, across data you haven't ingested yet, and merge it with knowledge from domains you haven't connected yet.

The practical path: arjuna computes → emits Turtle → vidya ingests into oxigraph → you query with SPARQL. The ontology is the contract between producer and consumer; everything else flows from it.

Right. So here's the honest comparison:

**You're not "limited" in what you store** — chart-db stores the full computed chart and extracts vectors from it. You encode all the information either way. The difference is in **what you can ask without writing new code**.

chart-db is optimized for two specific query shapes:
1. **Text/metadata search** — FTS on name/place/notes, filter by tags/collections/date
2. **Vector similarity** — "find charts that look like this one" via KNN on the feature vector

Those are powerful and fast. But if you want to ask "show me every chart where Mars is retrograde in the 12th house applying a square to Saturn within 2°" — that's not a KNN query and it's not a text search. You'd have to write custom Dart code to deserialize the full chart JSON, filter by those specific conditions, and iterate. Every new question shape = new code.

**With RDF in a SPARQL store**, that Mars/Saturn query is just:

```sparql
SELECT ?chart WHERE {
  ?chart oxa:hasPlacement ?mars .
  ?mars oxa:body oxa:Mars ; oxa:house 12 ; oxa:motion "retrograde" .
  ?chart oxa:hasAspect ?asp .
  ?asp oxa:body1 oxa:Mars ; oxa:body2 oxa:Saturn ;
       oxa:kind "square" ; oxa:applying true ;
       oxa:offset ?orb . FILTER(?orb < 2.0)
}
```

No new code. The triples are the index.

**But** — and this is the tradeoff — you still have to encode all the information as triples up front. The ontology design is the work: deciding that `oxa:motion` is a property, that `"retrograde"` is its value, that aspects are reified nodes with orb/applying/kind. That's what oxiephemeris-rdf's 5000 lines are doing. The encoding cost is real — it's just front-loaded into the ontology + serializer rather than spread across ad-hoc query code.

**So is it worth it for you?** The question is: how many novel query shapes do you anticipate? If chart-db's two modes (similarity + text) cover 90% of what aion needs, RDF is over-engineering. If you find yourself repeatedly wanting to query specific astrological conditions across a corpus — research questions, pattern mining, "find all charts matching this traditional configuration" — then RDF earns its keep because each new question is a query, not a feature.

The hybrid answer: chart-db for the fast UI path (similarity, browsing, collections), and an RDF export for the research/agent path when you want open-ended interrogation of the corpus. They don't have to be either/or.
